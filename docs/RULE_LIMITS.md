# Границы последовательностей и предыдущего события

12.11.2026: расширение подключений PostgreSQL/MySQL/MongoDB и форм описано в [SOURCE_CONNECTIONS.md](SOURCE_CONNECTIONS.md). Оно не меняет восемь механизмов, семантику последовательностей или предыдущего события. В каталоге событий появились необязательные `statuses`, в полях — `label` и `values` для вариантов конструктора. Это подсказки, не новый механизм и не автоматический запрет неизвестного статуса. Сохранённые значения старых правил остаются доступными при редактировании.

**Последовательность — порядок типов событий.** Между шагами допускаются другие события. Нет условий по данным каждого шага, сброса по отменяющему событию, поиска всех циклов или привязки соседних узлов дерева к конкретному найденному событию. Общий фильтр истории относится ко всем её событиям. При нескольких циклах правило «последовательность И сравнение с последним отказом» может использовать ранний цикл и более поздний отказ независимо. Нельзя описывать его как строгое обнаружение изменения между двумя определёнными шагами одного цикла.

**Предыдущее событие — существование факта.** Условие срабатывает, когда подходящего события нет. Рекомендуемые поля совпадения для проверки текущей версии — сумма, получатель и версия объекта. Если бизнес-процесс отзывает согласование без смены этих значений, одного поиска существующего события недостаточно: актуальное бизнес-состояние должно контролировать приложение. Решение о возможном расширении семантики отзыва оставлено отдельно; сейчас оно не реализуется и ТЗ под реализацию не переписывается.

**Связанные данные и И.** Историческое сравнение берёт последнее подходящее событие. При отсутствии истории это ошибка с запрещающим результатом. Все дети И/ИЛИ вычисляются; условие «есть отказ И сравнить с отказом» не является защитой от пустой истории. В примере 37 правило целиком исключается при отсутствии отказа до вычисления связанных сравнений.

**Доступность фактов.** Демо передаёт отдельные успешные действия `submit`, `approve`, `reject`, `pay`, `export`. Успешно выполненный отказ руководителя `reject` имеет статус SUCCESS. Заблокированная антифродом попытка не становится выплатой. Редактирование сохраняется в истории заявки, но не передаётся отдельным типом события движку. Поэтому цепочки заблокированных попыток и редактирований нельзя полностью восстановить по текущей таблице фактов.

Поведение закреплено в `backend/tests/test_rules.py`: подпоследовательность с промежуточным событием, отсутствие добавления текущего действия, совпадение актуальных полей и сохранение старого совпадающего согласования после отказа. Составные пары 37–38 дополнительно проверяются через реальный API в `backend/tests/http_demo_examples.py`.
